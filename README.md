# copy_fail.py — CVE-2026-31431 без `os.splice`
CVE-2026-31431 without os.splice — Python 3.6–3.9, ctypes instead of the 3.10-only API

Версия публичного PoC на CVE-2026-31431 («Copy Fail») для Python 3.6–3.9.

Оригинал на 732 байта вызывает `os.splice`, а он появился только в Python 3.10. На моей машине стоял 3.7, и скрипт падал на `AttributeError` ещё до первого сокета. Здесь `splice` дёргается через `ctypes` напрямую из libc.

Системный вызов при этом тот же самый — `os.splice` это лишь тонкая обёртка над `splice(2)`, а `libc.splice` вызывает его с теми же аргументами. Меняется только слой доступа, не механика.

## Что делает

Эксплуатирует logic-баг в шаблоне `authencesn`: при расшифровке он пишет 4 байта `seqno_lo` по смещению `assoclen + cryptlen`, то есть сразу за тегом аутентификации, и обратно их не восстанавливает. В `algif_aead` операция идёт in-place, а страницы тега приходят из `splice()` прямыми ссылками на page cache файла. Запись промахивается мимо выходного буфера и попадает в кэш целевого файла.

Скрипт заливает в кэш `su` (или любого другого setuid-бинаря) небольшой ELF-заголовок с `jmp` на шеллкод и делает `execve`. Бинарь сетьюидный, поэтому шеллкод стартует с `euid 0`, вызывает `setuid(0)` и отдаёт root-shell.

На диске ничего не меняется: страница не помечается dirty, кэш просто отдаёт подменённую версию. Ребут или `drop_caches` возвращают файл как было.

## Требования

- Linux, x86-64
- ядро ≥ 4.14 и без фикса `a664bf3d603d`
- доступный `AF_ALG` (дефолтный seccomp Docker его не режет, песочницы k8s и CI часто режут)
- загруженный модуль `authenc`
- любой читаемый setuid-root ELF64
- Python 3.6+ с `ctypes`

## Использование

```bash
chmod +x copy_fail.py

./copy_fail.py                 # патчит /bin/su и запускает его
./copy_fail.py -n              # только патч, без execve (сухой прогон)
./copy_fail.py /usr/bin/passwd # другая setuid-цель
